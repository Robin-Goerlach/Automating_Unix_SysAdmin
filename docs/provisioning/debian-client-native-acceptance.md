## Diagnostic tool

native-preflight.pl is read-only and standalone. Invoke as an ordinary user with trusted PATH and trusted file trees. Explicit --live selects the running system; --root=ABSOLUTE_DIR selects a non-root fixture tree and never runs runtime commands. Both require --hostname=lowercase FQDN (R2 maximum 63 characters) and --address=canonical IPv4. These are expected values from the operator-selected R2 record, not a separate inventory authority. The tool does not validate the inventory itself. It does not authorize writes, even if every observed value matches.

Example with documentation-only values:

    perl install/debian-client/native-preflight.pl --live --hostname=node.lab.invalid --address=192.0.2.40

Only with a real, operator-approved lab name and expected address, append --probe-name=FQDN --probe-address=IPv4. This opts into hostname -f and getent ahostsv4, which may cause network name lookups according to local NSS policy. No such lookup by default. The NSS probe requires exactly one distinct expected IPv4; a multi-address service is not this contract. It is not direct DNS evidence: files, NIS, caches or other NSS sources can answer. direct-dns always reports NOT_RUN.

The versioned TSV report SASD-NATIVE-PREFLIGHT-1 contains check/status/value; control bytes and percent signs are percent-encoded. Exit 0 means diagnostics emitted, NOT that the system passed; exit 2 is invalid invocation. UNKNOWN, OUT_OF_SCOPE, DRIFT and NOT_RUN require review. A detected VM/container is not proof that it is disposable. No secrets, resolver file contents or command lines from process listings are collected; hostnames and IPs are still private operational data. Command stderr remains separate. Linux timeout bounds live commands; missing tools or systemd bus are unknown, not evidence of inactive services. The conventional os-release link is mapped within the selected tree; file content is parsed, never sourced. Only trusted fixture trees (including ancestors and mounts) are supported, not a sandbox for hostile paths.

Resolver ownership is a hint, not a decision. Recognized symlinks and comments indicate systemd-resolved, NetworkManager, resolvconf or dhclient. A regular unmarked resolv.conf is UNKNOWN_REGULAR; it may be generated or overwritten. Service activity is supplemental only. Do not replace or unlink a managed resolver, disable a network manager, or assume static ownership because a service is inactive.

## Lab procedure (read-only until the experimental native writer is explicitly authorized)

1. Obtain the reviewed branch commit, check archive integrity against an independently trusted digest, and run G0. Use disposable VM console and an isolated lab VLAN/network, not production. Record snapshot identifier and demonstrate restoration on a disposable clone.
2. Select the real R2 record and site policy. Record expected FQDN, IPv4, DNS servers and an operator-maintained single-A test record not supplied by local hosts/NIS. Do not use .invalid or RFC 5737 addresses as live targets.
3. Capture preflight and existing verify-baseline.sh output (drift/unknown is expected before configuration). Record resolver symlink target, package ownership, service state, DHCP hooks and relevant network manager configuration manually. A regular file alone cannot establish ownership. Keep evidence privately.
4. Check the runtime resolver and direct DNS separately. On a VM with approved DNS tooling already installed, substitute actual lab values in the following read-only commands. Inspect exit codes, response status, queried server, answer owner/type and exact expected address; a successful dig exit alone does not establish success.

       getent ahostsv4 "$PROBE"
       dig +time=2 +tries=1 @"$DNS1" "$PROBE." A

   Repeat against each required DNS server. Use a single-A record with no CNAME for this initial acceptance. Require NOERROR and exact expected A answer; repeat with a known negative record and an isolated unreachable test server, without disrupting actual networking. NSS and direct DNS success are separate evidence. No public DNS resolver is assumed or contacted by the preflight by default.
5. Stop before native mutation. Future native writer must pass G3, then repeat G4–G6 from the console. Do not use fixture-apply against /, and do not bypass fixture guards. Restore snapshot if runtime connectivity or recovery cannot be verified.

## G5 preparation: direct DNS response verifier (M7-D.1e.2)

The native path requires /usr/bin/dig and /usr/bin/timeout already installed; no automatic package installation, no default resolver, no scanning. Example after selecting approved lab values:

## M7-D.1e.4a — read-only native change rehearsal (G3 preparation)

prepare-native.sh is an unprivileged review tool, not a native writer. Choose exactly one source: --live reads the running system, --source-root=ABSOLUTE_DIR reads a trusted fixture tree (not /). Both require --hostname=FQDN --inventory=FILE --roles=FILE --site=FILE. There is no apply flag. The live source must have root-owned regular target files; fixture files must be owned by the caller. The three fixed files are limited to 64 KiB each; group/other write permission, special mode bits, multiple links, symlinked targets and non-regular files are refused. Trusted and stable source directories, input files, local tools and code are required. The review accepts Debian 12/13 and UNKNOWN_REGULAR resolver hint only; this means ownership still needs proof, not that the resolver is static. No DNS/NSS probe is requested. No change to source files, hostname, services or network.

Example for an operator-selected host in a disposable VM (substitute actual approved inventory and site files):

    ./prepare-native.sh --live --hostname="$HOST" --inventory="$HOSTS" --roles="$ROLES" --site="$SITE"

The program validates the R2 plan, records the source file owner/group/mode/link-count/size and SHA-256, copies the original files and DNS policy into a private report, runs preflight, rehearses the existing grouped fixture transaction on disposable copies and compares the validated plan and source manifest again. The private /tmp/sasd-native-review.* report retains scope, source-root, created-utc, plan.tsv, source.tsv (name, colon-separated metadata, hash), preflight.tsv, site.conf, original/, desired/, desired.tsv, rehearsal-verify.tsv, rehearsal.log and changes.tsv. The successful status is PREPARED_NOT_AUTHORIZED; any incomplete report is not evidence of success. Exit 0 means the review was generated, not permission to write. Invalid/refused operations exit nonzero. Intermediate fixture and child report are removed on normal exit/handled signals; unhandled interruption can leave private temporary data. Retained reports contain internal configuration; protect and remove after review. This is not a native backup or recovery artifact: copies have caller ownership, only ordinary mode/content are compared; ACLs, xattrs, labels, inode identity, mount semantics and durable storage are not established. The sampled manifests detect observed differences, not all possible races or changes restored between samples. No live execution of this new tool was performed in this environment.

## M7-D.1e.4b.1 — synchronized fixture transaction foundation

Extend the existing fixture engine rather than duplicate it. GNU /usr/bin/sync with explicit path operands requests file/directory fsync on modern Linux. Before APPLYING, synchronize original targets, both retained snapshots, manifests, child directories, journal directory, fixture root and /tmp parent. For each replacement, verify staged contents and uid/gid/mode against the snapshot, synchronize the staged file before rename, then synchronize the target directory. Before COMMITTED or ROLLED_BACK, synchronize target files and directory again. Journal state is written to a temporary file, synchronized, renamed and the journal directory synchronized. Failure before target mutation stops apply; failure during replacement enters the existing rollback path. If a state rename succeeds but its directory sync fails, report JOURNAL SYNC UNCERTAIN, return failure and attempt to publish SYNC_FAILED. This is best-effort quarantine: when present it blocks automated apply/recovery and requires operator inspection; a storage failure can also prevent persisting that marker. Do not treat a visible terminal state after a reported sync failure as proof of durability. Do not delete the journal to force progress. Legacy journals are not retroactively durable. The existing manifest remains content/mode based; uid/gid are additionally checked when comparing files and staging replacements, not a full metadata manifest. No ACL/xattr/security-label guarantee.

## M7-D.1e.4b.3 — read-only native metadata and storage observations

## M7-D.1e.4c.2b — installation identity comparison

The optional modern Debian native-identity.py diagnostic compares two existing local identity files: /etc/machine-id (32 lowercase hex digits, nonzero) and /var/lib/sasd/provisioning/installation-id (canonical UUIDv4 assigned uniquely to each installation by the operator). It never creates, rotates or writes either file. Live reads expect root ownership; fixture reads expect caller ownership and reject root execution, a noncanonical path or /. Checked directory-relative opens refuse symlinks, unsafe owner/write/special mode bits, nonregular files, multiple links and identity files larger than 64 bytes. The read checks file identity and sampled size/mtime/ctime; trusted stable local directories and inputs are required. Not a complete ACL/mount/metadata or hostile-concurrency audit.

Use --live or --root=ABSOLUTE_FIXTURE, --hostname=R2_FQDN and --expected-installation=UUID. Optional --expected-fingerprint=SHA256 must come from an independently retained and operator-verified inventory reference, not the same cloned disk or an unreviewed report. Example using lab reference variables:

    ./native-identity.py --live --hostname="$HOST" --expected-installation="$INSTALLATION" --expected-fingerprint="$REFERENCE"

Without a fingerprint reference the tool emits an application-scoped correlation digest and UNBOUND (exit 3) for enrollment review only. The digest is SHA-256 over ASCII format tag, supplied inventory FQDN, installation UUID and machine-id separated by NUL bytes. No raw machine-id or installation UUID in normal report output. The FQDN is an operator-provided expected label, not a runtime hostname measurement or R2 inventory validation. The digest is not authentication or a secret; keep it and its reference private. MATCH (0) means the inputs correspond to the reference, MISMATCH (1) means they differ, UNKNOWN/UNBOUND (3) means evidence missing, unsafe, invalid or not independently bound; invalid CLI (2). native-apply always NOT_AUTHORIZED.

A new installation must receive an independent identity after cloning and be independently registered; do not copy enrollment references with images. A complete clone retaining all identity data can match the original, so the operator must still verify VM identity and unique enrollment against external inventory. No guarantee of clone detection, no TPM attestation, no signed reference, no runtime hostname or policy/release binding yet. The format is stable across runs when the identifiers persist, but an actual reboot has not been tested. This is a component for the later native transaction context, not yet a gate enforced by the fixture engine, collector or native writer. Native storage initialization, operator enrollment, release/policy binding and the privileged transaction backend remain open.

## M7-D.1e.4c.2d — experimental native static installer

native-install.py is the first separately implemented privileged native writer. It is NOT accepted for production or released for a VM yet. ### Operator and release contract

Do not invoke native apply before independent release review and G0–G2 acceptance on an isolated disposable Debian 12/13 KVM/QEMU VM with tested console/snapshot recovery. The program requires real/effective UID and effective GID 0, explicit --confirm-disposable-vm, and for --apply also --confirm-reviewed-gates (operator attestation of G0–G2 and verified static resolver ownership). These flags do not establish the facts themselves. It accepts no alternative root path. Independently verify the archive and expected runtime release digest before executing any code as root; a self-check by running code is not independent authentication. The fixed release path is /opt/sasd/debian-client with trusted root-owned non-writable-by-other directories and files, and the bundled R2 validator. Compare the deterministic runtime digest (lab-install.py release_digest(), including the new installer and shared renderer) in a reviewed independent environment. The program checks the runtime digest again before mutation. No signed release or authorization format is implemented.

The native provisioning storage and identity must be initialized separately by the operator after reviewing the VM. Existing root-owned /var/lib/sasd/provisioning/ contains installation-id, transactions/ and approved/; the latter two directories must be mode 0700. approved/ holds root-owned reviewed site.conf, hosts.tsv, roles.tsv and (for apply/recovery) authorization.json. No initialization or enrollment is performed by this writer. Preserve the reference and inputs for recovery. The fixed paths and initial filesystem profile deliberately exclude separate mounts, unsupported file flags and visible xattrs/ACLs/security labels. Target files must be regular, single-link, root:root, ordinary non-group/other-writable mode, at most 64 KiB, and no visible extended attributes. Full ACL/xattr/label preservation is not supported. Keep other administration and configuration managers quiescent; the lock is cooperative, not protection from independent root changes.

Review, apply and recovery require --hostname=FQDN --installation=UUID --fingerprint=SHA256 --release=SHA256 and --confirm-disposable-vm. Review checks native capabilities, identity, R2 inventory and preflight under a nonblocking exclusive flock on the existing transaction directory. For review/apply it also requires the expected IPv4 on the VM, an ordinary resolver file with no known manager marker and inactive NetworkManager/systemd-resolved/systemd-networkd. The operator must independently prove static resolver ownership; absence of hints does not do so. Review prints canonical JSON SASD-NATIVE-REFERENCE-1 (STATIC_LAB_ONLY) with expected FQDN, identity and release digests, input hashes, plan hash and original/desired snapshot digests. Inspect original and proposed configuration separately with the previously developed read-only review procedure; the new native review output contains hashes, not a human-readable diff. Only after independent review may that exact JSON be installed as approved/authorization.json by the operator. --apply additionally needs --confirm-reviewed-gates. Inputs and source/soll snapshots are checked against the authorization; this is not a cryptographic signature or replay protection. Do not use fixture reference files. The actual native CLI has not been exercised on a VM and is not authorized for use until the outstanding gates are addressed.

### Transaction and recovery contract

Under the same lock, persist native.UUID.json (SASD-NATIVE-JOURNAL-1, mode 0600) with reference and both snapshots (hex content and ordinary mode; UID/GID fixed to root). Journal states APPLYING, ROLLING_BACK, COMMITTED_STATIC and ROLLED_BACK. Write temp file in its destination directory, fsync data/metadata, rename, fsync directory; first synchronize journal containing original and desired before changing any target. Recheck original content/mode before replacement, retain both snapshots, compare the final snapshot and run the static verifier, then persist COMMITTED_STATIC. Individual replacements are atomic, not the three-file operation. No automatic rollback on failure; inspect journal and explicitly recover. --recover=native.UUID.json accepts only the sole open journal, same independently approved reference and verified identity/release/input context, and every current target must equal the original or desired snapshot; restore original bytes and ordinary modes, verify and persist ROLLED_BACK. Closed journals cannot be rolled back by this interface; after a successful static commit with later DNS/runtime failure, use the reviewed console/snapshot fallback pending a separate committed rollback procedure. If a journal sync fails, best-effort SYNC_FAILED quarantine; any unexpected journal-store entry (including leftover temp files) blocks automatic progress. A storage failure may prevent the quarantine itself from persisting; do not infer durability from a visible terminal state after error. Do not remove journals or quarantine to force progress. G6 requires actual VM crash/reboot and snapshot restoration evidence. Timestamps, exact inode metadata and runtime hostname are not restored by this static transaction.
