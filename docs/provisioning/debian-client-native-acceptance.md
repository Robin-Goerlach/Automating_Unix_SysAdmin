# Native Debian baseline acceptance contract (M7-D.1e)

Deutsch: [Deutsche Fassung](debian-client-native-acceptance.de.md)

Status: **PREPARATION ONLY — native apply not implemented or authorized.** Modern Debian profile only; the historical path is unchanged. See [client design](debian-client.md).

## Diagnostic tool

native-preflight.pl is read-only and standalone. Invoke as an ordinary user with trusted PATH and trusted file trees. Explicit --live selects the running system; --root=ABSOLUTE_DIR selects a non-root fixture tree and never runs runtime commands. Both require --hostname=lowercase FQDN (R2 maximum 63 characters) and --address=canonical IPv4. These are expected values from the operator-selected R2 record, not a separate inventory authority. The tool does not validate the inventory itself. It does not authorize writes, even if every observed value matches.

Example with documentation-only values:

    perl install/debian-client/native-preflight.pl --live --hostname=node.lab.invalid --address=192.0.2.40

Only with a real, operator-approved lab name and expected address, append --probe-name=FQDN --probe-address=IPv4. This opts into hostname -f and getent ahostsv4, which may cause network name lookups according to local NSS policy. No such lookup by default. The NSS probe requires exactly one distinct expected IPv4; a multi-address service is not this contract. It is not direct DNS evidence: files, NIS, caches or other NSS sources can answer. direct-dns always reports NOT_RUN.

The versioned TSV report SASD-NATIVE-PREFLIGHT-1 contains check/status/value; control bytes and percent signs are percent-encoded. Exit 0 means diagnostics emitted, NOT that the system passed; exit 2 is invalid invocation. UNKNOWN, OUT_OF_SCOPE, DRIFT and NOT_RUN require review. A detected VM/container is not proof that it is disposable. No secrets, resolver file contents or command lines from process listings are collected; hostnames and IPs are still private operational data. Command stderr remains separate. Linux timeout bounds live commands; missing tools or systemd bus are unknown, not evidence of inactive services. The conventional os-release link is mapped within the selected tree; file content is parsed, never sourced. Only trusted fixture trees (including ancestors and mounts) are supported, not a sandbox for hostile paths.

Resolver ownership is a hint, not a decision. Recognized symlinks and comments indicate systemd-resolved, NetworkManager, resolvconf or dhclient. A regular unmarked resolv.conf is UNKNOWN_REGULAR; it may be generated or overwritten. Service activity is supplemental only. Do not replace or unlink a managed resolver, disable a network manager, or assume static ownership because a service is inactive.

## Lab procedure (read-only until a reviewed native writer exists)

1. Obtain the reviewed branch commit, check archive integrity against an independently trusted digest, and run G0. Use disposable VM console and an isolated lab VLAN/network, not production. Record snapshot identifier and demonstrate restoration on a disposable clone.
2. Select the real R2 record and site policy. Record expected FQDN, IPv4, DNS servers and an operator-maintained single-A test record not supplied by local hosts/NIS. Do not use .invalid or RFC 5737 addresses as live targets.
3. Capture preflight and existing verify-baseline.sh output (drift/unknown is expected before configuration). Record resolver symlink target, package ownership, service state, DHCP hooks and relevant network manager configuration manually. A regular file alone cannot establish ownership. Keep evidence privately.
4. Check the runtime resolver and direct DNS separately. On a VM with approved DNS tooling already installed, substitute actual lab values in the following read-only commands. Inspect exit codes, response status, queried server, answer owner/type and exact expected address; a successful dig exit alone does not establish success.

       getent ahostsv4 "$PROBE"
       dig +time=2 +tries=1 @"$DNS1" "$PROBE." A

   Repeat against each required DNS server. Use a single-A record with no CNAME for this initial acceptance. Require NOERROR and exact expected A answer; repeat with a known negative record and an isolated unreachable test server, without disrupting actual networking. NSS and direct DNS success are separate evidence. No public DNS resolver is assumed or contacted by the preflight by default.
5. Stop before native mutation. Future native writer must pass G3, then repeat G4–G6 from the console. Do not use fixture-apply against /, and do not bypass fixture guards. Restore snapshot if runtime connectivity or recovery cannot be verified.

## G5 preparation: direct DNS response verifier (M7-D.1e.2)

verify-dns.pl is a separate read-only probe for one operator-approved lab A record. No query is sent without explicit --live; --fixture=FILE parses synthetic dig output and never contacts a server. Both require --server=IPv4 --name=lowercase.fqdn --expected=IPv4. Use actual lab values, not the reserved example addresses. The native path requires /usr/bin/dig and /usr/bin/timeout already installed; no automatic package installation, no default resolver, no scanning. Example after selecting approved lab values:

    perl install/debian-client/verify-dns.pl --live --server="$DNS1" --name="$PROBE" --expected="$EXPECTED"

Repeat for each required resolver. The program invokes dig without a shell, ignores .digrc, uses an absolute query name, bounds execution and output, and requires a single response header, response flag, untruncated response, matching server/question, NOERROR and precisely one A answer for the requested owner and expected IPv4. CNAME and multiple-answer services are outside the first acceptance scope. It does not validate DNSSEC, server identity cryptographically, NSS behavior, or all DNS records. Its text parser is intentionally strict: unfamiliar output is not evidence. Run the independent NSS probe described above as well.

SASD-DNS-VERIFY-1 reports scope, server, name, expected, status and reason. Exit 0 with LIVE_DNS/MATCH is a point-in-time direct DNS observation only, not native acceptance. Exit 0 with FIXTURE_ONLY/FIXTURE_MATCH is synthetic evidence only. Exit 1 = mismatch, 2 = invalid input, 3 = unknown/tool failure or ambiguous context. The native preflight still reports direct-dns NOT_RUN because it does not invoke this separate opt-in tool. No verified-task ledger accepts either result yet. Keep reports private.

## M7-D.1e.4a — read-only native change rehearsal (G3 preparation)

prepare-native.sh is an unprivileged review tool, not a native writer. Choose exactly one source: --live reads the running system, --source-root=ABSOLUTE_DIR reads a trusted fixture tree (not /). Both require --hostname=FQDN --inventory=FILE --roles=FILE --site=FILE. There is no apply flag. The live source must have root-owned regular target files; fixture files must be owned by the caller. The three fixed files are limited to 64 KiB each; group/other write permission, special mode bits, multiple links, symlinked targets and non-regular files are refused. Trusted and stable source directories, input files, local tools and code are required. The review accepts Debian 12/13 and UNKNOWN_REGULAR resolver hint only; this means ownership still needs proof, not that the resolver is static. No DNS/NSS probe is requested. No change to source files, hostname, services or network.

Example for an operator-selected host in a disposable VM (substitute actual approved inventory and site files):

    ./prepare-native.sh --live --hostname="$HOST" --inventory="$HOSTS" --roles="$ROLES" --site="$SITE"

The program validates the R2 plan, records the source file owner/group/mode/link-count/size and SHA-256, copies the original files and DNS policy into a private report, runs preflight, rehearses the existing grouped fixture transaction on disposable copies and compares the validated plan and source manifest again. The private /tmp/sasd-native-review.* report retains scope, source-root, created-utc, plan.tsv, source.tsv (name, colon-separated metadata, hash), preflight.tsv, site.conf, original/, desired/, desired.tsv, rehearsal-verify.tsv, rehearsal.log and changes.tsv. The successful status is PREPARED_NOT_AUTHORIZED; any incomplete report is not evidence of success. Exit 0 means the review was generated, not permission to write. Invalid/refused operations exit nonzero. Intermediate fixture and child report are removed on normal exit/handled signals; unhandled interruption can leave private temporary data. Retained reports contain internal configuration; protect and remove after review. This is not a native backup or recovery artifact: copies have caller ownership, only ordinary mode/content are compared; ACLs, xattrs, labels, inode identity, mount semantics and durable storage are not established. The sampled manifests detect observed differences, not all possible races or changes restored between samples. No live execution of this new tool was performed in this environment.

### Native writer contract (design only, not implemented)

1. Select one disposable VM and record G0–G2 evidence, including a tested console and snapshot restore. Operator proves actual static resolver ownership by reviewing manager configuration, DHCP hooks and package state; absence of a marker or inactive service is insufficient. Review the actual changes and expected DNS/NSS data; refuse unresolved ownership. First target is identity/static resolver only; managed resolvers require separate adapters.
2. Future privileged entrypoint must be separate from the fixture tools. Use trusted root-owned immutable-for-unprivileged-users code and reviewed input snapshots, fixed trusted executable paths/environment, explicit console-confirmed lab operation and machine/commit/policy identity binding. Do not execute or trust a user-generated review as a privileged instruction. Re-derive and compare expected plan under the same lock immediately before mutation; reject stale or conflicting state.
3. Verify directories, target owners, permissions, links, filesystem/mount boundaries, ACLs, xattrs and applicable security labels. Reject unsupported metadata and nonreplaceable targets; do not silently normalize. Hold exclusive administration lock through backup, apply, verification and evidence. Prevent competing manager writes by choosing a proven static configuration, not disabling managers automatically.
4. Persist original contents and metadata, prior runtime hostname, desired contents, context and journal in a protected durable location outside /tmp. Define and test fsync ordering for snapshots, state changes, same-filesystem staged renames and directory entries. No multi-file atomicity claim. Before first change ensure restoration prerequisites and sufficient storage. Do not consume the original snapshots during replacement.
5. Apply only reviewed files, preserving unrelated entries; update runtime hostname through a separate reviewed mechanism. Verify installed content and metadata, runtime hostname/FQDN, existing IP/management reachability, direct DNS and NSS separately. No IP reconfiguration, service activation, packages, firewall, central registration or auto-reboot in this operation. A failed check initiates recovery, not completion.
6. Recovery must support interrupted apply and rollback from a durable journal, restore original metadata and runtime hostname, refuse unknown external edits, block new writes while unresolved, and provide console/snapshot fallback. Test normal, unchanged repeat, induced failure, SIGKILL, reboot and snapshot restoration before acceptance. Power-loss behavior and failure of rollback require explicit tests and documentation. Native state, fixture reports and runtime verification must never be interchangeable.

## M7-D.1e.4b.1 — synchronized fixture transaction foundation

Extend the existing fixture engine rather than duplicate it. GNU /usr/bin/sync with explicit path operands requests file/directory fsync on modern Linux. Before APPLYING, synchronize original targets, both retained snapshots, manifests, child directories, journal directory, fixture root and /tmp parent. For each replacement, verify staged contents and uid/gid/mode against the snapshot, synchronize the staged file before rename, then synchronize the target directory. Before COMMITTED or ROLLED_BACK, synchronize target files and directory again. Journal state is written to a temporary file, synchronized, renamed and the journal directory synchronized. Failure before target mutation stops apply; failure during replacement enters the existing rollback path. If a state rename succeeds but its directory sync fails, report JOURNAL SYNC UNCERTAIN, return failure and attempt to publish SYNC_FAILED. This is best-effort quarantine: when present it blocks automated apply/recovery and requires operator inspection; a storage failure can also prevent persisting that marker. Do not treat a visible terminal state after a reported sync failure as proof of durability. Do not delete the journal to force progress. Legacy journals are not retroactively durable. The existing manifest remains content/mode based; uid/gid are additionally checked when comparing files and staging replacements, not a full metadata manifest. No ACL/xattr/security-label guarantee.

Local exact base provisioning tree fe86369a879f64a72346e58f0b9e64b81bf78193 and R2 validator 5a1b56ba793ae92b75a6fb13a9dbe00c2b3cd22c verified. test-durability.sh uses real sync and test-only fault injection into a separate private script copy (no runtime hooks). It verifies ordering, failure before mutation, staged-file sync failure, terminal journal directory sync failure and a blocked subsequent apply, and actual SIGKILL during rollback followed by recovery of all original content and basic uid/gid/mode. Complete provisioning test.sh passed as nobody, exit 0, including the 135-file archive exercise. Tests ran in Debian 13 on overlayfs; this is NOT evidence of actual power-loss durability, persistent native journal storage or successful fsync under every filesystem.
