# Debian client configuration — M7 extension proposal

Deutsch: [Deutsche Fassung](debian-client.de.md)

This modern Debian 12 reference profile is independent of the historical runtime. It is derived from an operator-provided 2026 installation checklist; the private original is not redistributed. Each of its 116 marked items has a separate numbered task and a source-line entry in the traceability catalog. Initial code is a candidate generator, not a live installer. No native acceptance or release claim.

## Architecture and task contract

M6 PXE/DHCP/TFTP installs the base OS; HTTPS distributes a versioned postinstallation bundle; the task runner configures the selected host in a future accepted apply mode; M7 generates a new identity and pending monitoring request using the existing approval mechanism. No parallel enrollment database or automatic approval.

The R2 inventory remains the authoritative host registry: hostname, address, role, groups and profile are entered once. Future site-profile and per-host data extend this through validated text files keyed by hostname; DNS, NIS hosts/netgroups/ethers, automounter, monitoring, mail, backup and machine aliases are generated by central adapters. A client never edits central servers as root. Separate review/apply and rollback are required. No SQL dependency.

The dispatcher discovers four-digit task names in lexical order (0010, 0020, ...); four digits were chosen to leave gaps for over 100 tasks. Each task is independently callable with --dryrun (alias --dry-run), --hostname=FQDN, --site=FILE and --render. A task's number sets ordering, not its dependencies; future real apply must enforce explicit prerequisite IDs before mutation. The current order is a reviewable candidate ordering, not a live dependency graph. Pre-install and central entries appear as manual/central report rows, not actions. Task scripts use a small local library, no eval or shell-sourced site file.

Dry run performs no writes. Stage mode generates private, flat candidate files under a newly created /tmp directory, never /etc; root staging is refused. Task exit 0 = rendered, 10 = planned, 20 = deferred, 21 = manual, 22 = central, 23 = review; all other codes stop the runner, which marks subsequent tasks NOT RUN. Runner exit 0 = selected tasks have no open entries, 1 = failure, 2 = usage/preflight, 3 = incomplete checklist. Candidate files are not installed or automatically trusted. A full checklist is intentionally incomplete. Staging is not actual installation. Nine renderers cover resolver, hostname, hosts, two conservative package lists, login banner, shell policy, sysstat and logwatch; package availability is not verified. Remaining task files are explicitly non-executing placeholders, not implemented installation commands.

## Usage

```sh
cd install/debian-client
./install-client.sh --list
./install-client.sh --hostname=node.lab.invalid --site=site.example.conf --dryrun
./install-client.sh --hostname=node.lab.invalid --site=site.example.conf --stage
./tasks/0010_DNS_Client_Set_Name_Server --hostname=node.lab.invalid --site=site.example.conf --render
./test.sh
./package.sh /tmp/new-sasd-debian-release
```

Save stdout to a private report with shell redirection if desired; the runner does not pretend a rendered task has succeeded on the OS. A full run returns 3 until outstanding tasks are resolved. Archive packaging creates a new directory, excludes runtime configuration and emits SHA-256. Publish the exact reviewed version through authenticated HTTPS. Pin the archive digest through a separately trusted channel (or verify a signature with a preinstalled trusted public key); a checksum downloaded from the same untrusted server is insufficient. Fetch to a private directory using curl with HTTPS verification, verify before extraction, review archive names, extract unprivileged and run dry-run. Never curl | sh. No automatic TFTP execution, untrusted archives, passwords or private keys. M6 installer hook integration remains pending.

## Required implementation sequence and acceptance gates

1. Baseline: preflight actual Debian release, OS identity, target hardware/VM, inventory consistency and installer evidence. Select DHCP/static networking backend and resolver owner (NetworkManager, ifupdown, resolved); preserve active connectivity. Implement atomic managed files, original backup, diff, validation and repeat-run checks. No network restart over SSH without recovery console. Preserve existing /etc/hosts IPv6 and unrelated lines.
2. Package stage: validate bookworm package names and signed APT sources, install selected profiles with noninteractive debconf and safe service-start policy; record dpkg/apt result and reboot-needed state. Never downgrade or blindly change repositories. Separate baseline/desktop/laptop/server/security/legacy. No blanket unattended kernel skipping. Test each apt group.
3. Core services: choose one logging backend (rsyslog or syslog-ng), one firewall manager, one identity provider per role. SSH validate with sshd -t and retain access; system-wide known hosts belong in ssh_known_hosts, not ssh_config. Firewall requires loopback and established/related, IPv6 policy, explicit inbound allowlist and atomic persistence with timed recovery. SMTP null client uses Debian Postfix main.cf/postconf; aliases require newaliases. Cron jobs use managed files and do not duplicate distro timers.
4. Storage, NFS and identity: never write disk/GRUB/USB by default. Validate fstab before mounting, preserve UUID and existing mounts, prefer hard NFS where appropriate; protect /home noexec policy against application needs. NIS/NSS/PAM, LDAP/AD, SELinux, USBGuard and bootloader are opt-in separate isolated gates; no wildcard NIS shadow/passwd injection, no blind PAM edits or shared credentials. Never copy SSH private keys. Use verified host-key distribution, role-specific authorization, secure secrets outside repo/logs.
5. Monitoring, security and scheduled jobs: device-aware SMART/NVMe, sensors reviewed, single ClamAV updater, audit rules validated, AIDE baseline only after installation, no uncontrolled recurring duplicates. Puppet, Monit, Big Sister and SNMP are distinct optional adapters, not replacements for M7 pending enrollment. ReaR backup and restore only to verified disposable targets. Legacy software/version availability and licensing require checks.
6. Central registration and inventory: derive service configurations from R2 input, show central changes before privileged apply, reject duplicate identities, support remove/disable and retry, record approval and reconciliation. Inventory captures hardware/MAC/serial/disks/RAM/owner/assets and installer evidence with restricted access; never records root password or disk passphrase. Warranty, peripheral, user-data restore and workstation checks remain manual as appropriate.
7. Native KVM acceptance: run isolated Debian 12 guest from M6; verify archive digest; dry-run; staged candidates; implement actual --apply only behind explicit lab gate and root/OS checks, per-task backups/validation/rollback, concurrency lock and resume across controlled reboots. Test first run, second run idempotence, failed prerequisite, package failure, SSH/firewall recovery, tampered bundle, wrong host, interrupted/reboot resume, central registration rejection, M7 approval. Only then authorize production deployment. Store redacted evidence outside public Git. No tests or native results are asserted by this proposal.

## Fixture-only baseline application (M7-D.1a)

The shared lib/policy.sh supplies one hostname and static DNS validator for rendering, verification and fixture application. apply-baseline.sh is deliberately separate from the dispatcher. It accepts --root=DIR, --hostname=FQDN, --site=FILE and --dryrun (default) or --apply. It refuses UID 0, real /, paths outside a direct /tmp/sasd-debian-lab.ALPHANUM child, non-private or foreign-owned directories, missing fixture marker (SASD-DEBIAN-FIXTURE-1), symlinked or multiply linked targets. Only trusted disposable fixture trees are supported; not adversarial concurrency or mounts.

The three regular fixture files etc/hostname, etc/hosts and etc/resolv.conf must already exist. A short original hostname is required. Ambiguous 127.0.1.1 entries or additional aliases are refused, rather than silently removed; unrelated host entries, IPv6 lines and inline comment on the recognized mapping are preserved. Resolver options and non-policy lines are retained; nameserver/search/domain directives are replaced with the validated static policy. Whitespace and trailing newlines may be normalized. Apply locks the fixture, copies originals and modes into a private transaction directory, validates the entire candidate, then replaces changed files via individual renames and verifies again. Unchanged target files are not replaced; a second run still creates a new backup directory. Detected failures and handled signals attempt rollback; process kill, power loss, multi-file atomicity, ACL/xattr preservation and durable crash recovery are NOT guaranteed. No packages, kernel hostname, services, network, DNS queries, or live files are changed. A stale lock and retained backups require operator review.

Run `sh install/debian-client/test-apply.sh` from the repository root as a non-root user for a fully disposable example; test.sh also invokes it. Root execution reports SKIPPED in the test and is refused by the apply tool. Local test in a Linux container as nobody passed: dry-run no writes, three changes, byte-identical backups, unrelated entries and modes preserved, second run unchanged, conflicting entry, symlink, hardlink, lock and real-root rejection, and induced post-apply verification failure with restoration of previous SHA-256 hashes. Native Debian, full repository CI, and dispatcher apply remain open.

## M7-D.1b — retained transaction journal and explicit recovery

This supersedes the previous fixture lock/rollback implementation. Linux util-linux flock on the private fixture directory serializes cooperating writers and recovery (also dry-run); the descriptor is released when all inheriting processes exit. Legacy .baseline-lock markers require operator review, never automatic removal. The separate lib/transaction.sh supports a fixed three-file manifest, not a generic privileged file installer.

Before any target mutation, apply retains original/ and check/etc/ snapshots, original.tsv and desired.tsv (fixed name, octal mode, SHA-256), and atomically replaces the state file. PREPARING means no target mutation has begun; APPLYING means the target may be partially installed; COMMITTED means verified target content/modes; ROLLING_BACK means an incomplete rollback may exist; ROLLED_BACK means original content/modes verified. No new apply while an APPLYING or ROLLING_BACK journal exists. Multiple open or unknown journals fail closed. Legacy backups without state are not recoverable by this protocol. Do not delete journals manually to bypass the gate.

Inspect the reported baseline.* directory and its manifests. For a trusted disposable fixture only, run recover-baseline.sh with --root=DIR --transaction=baseline.ID --dryrun, then repeat with --apply after review. Recovery only accepts the sole open transaction; committed or already rolled-back transactions are refused. It validates both retained snapshots, and all three current files must individually match their original or desired content and mode before any restore. Unexpected edits cause refusal without mutation. The same restore is used by the handled-error cleanup. A partly completed rollback can be retried. Exit 0 = planned/completed, 2 = invalid/refused, 1 = incomplete recovery. No site secrets or real system paths are needed.

Local unprivileged Linux tests test-recovery.sh and test-interruption.sh passed. The latter injects real SIGKILL into an isolated copy of apply-baseline.sh after replacements, proves the next apply is blocked, restores the initial manifest, then verifies reapply and an unchanged repeat. The former simulates a partially applied fixture and ROLLING_BACK state; checks dry-run, backup mismatch, independent edit, competing lock, ambiguous journal, committed/recovered refusal and real-root rejection. Exact tested script blobs are checked before publishing. Full make test, native Debian and CI remain unverified. No fsync/power-loss guarantee, no authenticated journal (trusted private fixture only), no hostile same-UID writer protection, no automatic pruning, no automatic reboot/resume or generic multi-file atomicity. Temporary staging files and PREPARING journals may remain after hard kill. Historical runtime is unchanged.

## M7-D.1c — central inventory and dependency planning

The standalone read-only plan-client.pl uses the existing repository bin/sasd-site-inventory to validate one R2 host snapshot. It requires --inventory=HOSTS.tsv --roles=ROLES.tsv --hostname=FQDN, optionally --only=NNNN. Select an existing R2 record with lowercase FQDN (R2 limit 63 characters) and OS family debian. Role, groups, profile and IPv4 come from the selected inventory record, not separate CLI overrides. The planner also rejects case-insensitive duplicate names and noncanonical IPv4 throughout the validated snapshot. The inventory is operator-provided and trusted; this is not authentication of the physical machine, validation of runtime network settings or a new inventory format.

dependencies.tsv contains an initial set of 23 explicit prerequisite edges, not a complete operational dependency graph. Every prerequisite ID must be lower than its dependent ID, so cycles and contradictory numbering are refused. The catalog and actual task filenames must agree exactly; missing, duplicate, symlinked or unexpected tasks fail closed. A candidate edge refers only to a render-capable prerequisite; a verified edge requires future evidence of actual installed state. The planner recursively includes all prerequisites when --only is specified. Candidate prerequisites that are themselves blocked propagate WAIT_CANDIDATE; verified edges always result in WAIT_VERIFIED in this version. PLAN_CANDIDATE is a planning classification, not generated content or completion. Other categories remain visible. No task is executed, no verification evidence is accepted or fabricated, and no file is written by the planner. Exit 0 means a structurally valid plan, even with unresolved entries; invalid input exits nonzero. Output is versioned text with an R2 host record and TSV task rows.

Example using an operator-maintained R2 inventory containing a Debian record:

    perl install/debian-client/plan-client.pl --inventory=/path/to/hosts.tsv --roles=/path/to/roles.tsv --hostname=node.lab.invalid --only=0040

The plan is repository-side only (needs the existing R2 validator); it is deliberately not yet shipped in the standalone tarball. The dispatcher continues its earlier independent candidate behavior. Neither task enforcement, role-specific applicability, nor a verified completion ledger is implemented yet. Direct calls to individual tasks remain unchanged. M7-D.1d must integrate planning and enforce actual evidence before enabling fixture execution. Revisit dependency policy for all 116 entries before native apply.

Local test-plan.sh ran successfully as nobody with exact copies of the published R2 validator and 116-row catalog, and synthetic task files with the published names (failing scripts, never executed). Tests cover selected closure, verified waiting, transitive candidate blocking, unknown hosts/tasks, duplicate names and addresses, noncanonical IPv4, incorrect OS/profile, forward/duplicate/missing dependency, missing/symlink/extra task, and no task invocation. Full repository tests, native Debian and CI remain unverified.

## M7-D.1d.2 — transaction-backed fixture baseline dispatcher

Explicit --fixture-apply --root=FIXTURE --hostname=FQDN --site=FILE --inventory=FILE --roles=FILE selects dispatch-fixture.sh via install-client.sh regardless of option order.     install/debian-client/install-client.sh --fixture-apply --root=/tmp/sasd-debian-lab.EXAMPLE --hostname=node.lab.invalid --site=/path/to/site.conf --inventory=/path/to/hosts.tsv --roles=/path/to/roles.tsv

## M7-D.2a — package stages: local APT plan (0200 and 0730)

The optional modern Debian Python 3 tool plan-packages.py evaluates the existing candidate rows from package-policy.tsv (stage 1: 19; stage 2: 15; no optional/review/server/laptop/duplicate entries selected). Both lists are checked against the corresponding independent task renderers by tests. No policy expansion or real install. Run as an ordinary user against trusted local APT configuration and metadata:

    ./plan-packages.py --live --stage=1
    ./plan-packages.py --live --stage=2
    ./plan-packages.py --live --stage=both --simulate

The default stage is both. apt-cache policy uses fixed executable paths, a minimal C-locale environment, disabled binary package-cache files and a 60-second timeout per subprocess. No apt update, package download or write operation is requested. The TSV report associates task, package, status, installed and candidate version. INSTALLED_SAME and CANDIDATE describe APT metadata, not proof of a healthy dpkg state, downloadable packages or verified repository provenance. NO_LOCAL_RECORD/NO_LOCAL_CANDIDATE mean the local metadata is insufficient, not that the package is unavailable on Debian. VERSION_REVIEW flags a differing candidate, including possible downgrade; UNKNOWN marks command/parse failures. Raw APT output and repository locations are not emitted.

--simulate is explicit and runs only if all selected rows have candidates and no version-review condition. It invokes apt-get --simulate --no-install-recommends --no-remove install with the selected names; only action counts are reported, not a complete dependency lockfile. APT summary and action counts must agree; upgrades, removals, existing-version changes or unknown output prevent a successful simulation claim. The simulation does not execute maintainer scripts, install packages, resolve actual service effects or prove that subsequent installation will work; local APT metadata may be stale or change during the run. The two-stage combined simulation is not a staged execution plan. No automatic installation, repository changes, release authentication or package task completion evidence. Exit 0 means observations/simulation without detected blocker, 3 review/block/unknown, 2 invalid invocation or policy. package-apply always NOT_AUTHORIZED. Existing dispatcher and catalog states are unchanged; 0730 is not verified and 0790 remains gated.
